1. What it is for

Today a person takes the numbers out of their accounting program, copies them into the Excel template and uploads it to BUFINS. The ingestion API lets a program make that submission on its own, without changing anything BUFINS already does with the data: it is validated with the same rules, a backup is kept before replacing anything and everything is audited.

For the client's IT team
  • A REST API with JSON, one key per integration and an OpenAPI contract.
  • Ready-to-use examples in curl, PowerShell, Python and C#.
For the company administrator
  • Creates and revokes keys in Configuration → API integrations.
  • Decides whether the integration can confirm, or whether a person always does.
For the accountant or analyst
  • Reviews each submission in “Review load”, as with Excel.
  • Gets a bell-icon notification when a load is waiting.

Important. The API delivers the data; reports are updated when the models are run, just as today. A submission through the API skips no validation and never bypasses the rule of never leaving a year empty.

Option B · Sheets as JSON

The program opens a load, sends the data of each sheet as JSON (in batches if large) and closes it. No Excel needed.

For direct ERP integrations

What the API guarantees

  • All or nothing. A load only changes the real data when it is confirmed; until then it lives apart (staging).
  • Backup and undo. Before replacing, BUFINS saves the previous version; an administrator can undo from the version history.
  • Golden rule. No load can leave a year empty or reduce a table below the blocking threshold; a strong reduction is always confirmed by a person.
  • A new submission replaces the pending one from the same integration for the same company: unreviewed submissions do not pile up.

3. Before you start: create the integration

The key is created by a company administrator (or a BUFINS one). It is done once for each system that will send data.

  1. Go to Configuration → API integrations and click New integration.
  2. Choose the company, type a name that identifies the system (for example “Siigo agent – accounting”) and choose the technical user. We recommend creating a dedicated user (“API integration”): the API's actions are recorded in the audit log under that name. It cannot be a Super Admin.
  3. Optional: enter the allowed IPs (the addresses the client will send from). With the list, the key only works from them.
  4. Leave “Allow the integration to confirm loads and run the models” unchecked during testing: that way every submission stays in “Review load” and a person confirms it.
  5. Click Create. BUFINS shows the key only once: copy it and store it in the client's secrets manager. If it is lost, a new one is generated.

Key format: bfk_xxxxxxxx_… in production and bft_xxxxxxxx_… for testing. Treat it like a password: do not send it by email or keep it in source code.

Testing environment (sandbox)

Before connecting the real system, the client's team can develop and test with a Testing integration (the “Integration type” field when creating it). It uses a key that starts with bft_ and works like a production one (same endpoints, same format, same validations, findings, impact and rules), with these differences:

  • Confirmation is a simulation. POST /cargues/{id}/confirmar (or confirmar=true) runs all the checks, including the rule of never leaving a year empty and the strong-reduction check, and responds ConfirmadoSimulado. It replaces no data, saves no backup and the test load is discarded.
  • Reviewers are not notified: a test load creates work for nobody.
  • They are short-lived and do not get in the way. A test load is discarded on its own after a few hours and never prevents another person from loading the same company and year.
  • It shows in every response: they carry the header X-Bufins-Entorno: pruebas and /ping answers "entorno": "pruebas".
  • Its own technical user. It cannot be the same user as a production integration.

Validations and impact are computed against the company's real data, read-only: that way tests catch the same problems the real submission would have. When everything works, the administrator creates the Production integration and the client only changes the key: the address is the same. If there is a real load pending review for the same year and mode, a test submission gets 409 lote_activo: confirm or discard that load, or test with another year.

The names of the sheets and columns each company accepts are always obtained with GET /api/v1/esquemas (section 5): a new custom sheet appears there with no API changes.

4. Security

IsolationThe company comes from the key, never from what the client sends. Each integration only sees and touches its own loads; if it asks for someone else's it gets “not found”.

Rotate and revokeRotating generates a new key and the old one stops working instantly. Revoking is permanent (create another integration if needed).

If the key leaks: go to API integrations and use Generate new key (or Revoke). The effect is immediate.

Folder agent: automatic submission without programming

If the client's accounting system can drop the Excel template into a folder (or someone copies it there), nothing needs to be programmed: the BUFINS agent (AgenteBufins.exe, a single file, no .NET to install) watches that folder and uploads each file through this same API. It only makes outgoing https connections: no port is opened on the client's server. BUFINS provides the agent on request.

  1. Copy AgenteBufins.exe and agente.ejemplo.json to a folder on the server (for example C:\BUFINS\Agente), rename the example to agente.json and adjust it: the folder to watch (for example C:\BUFINS\Entrada), the year, the mode and the scenario.
  2. Store the integration key: AgenteBufins.exe --guardar-clave. It is saved encrypted in clave.dat and can only be read by that machine (the BUFINS_CLAVE environment variable is also supported). The key is never written to agente.json or to the logs.
  3. Check the connection: AgenteBufins.exe --probar shows the integration, the company and whether the environment is testing or production.
  4. Put it to work: as a Windows service (sc.exe create BufinsAgente binPath= "C:\BUFINS\Agente\AgenteBufins.exe" start= auto and then sc.exe start BufinsAgente) or with the Task Scheduler running AgenteBufins.exe --una-vez at each close.

What happens to each fileResult
BUFINS accepts itIt moves to procesados\ together with the response (.resultado.json). It stays pending review, or confirmed if the integration may and "confirmar": true.
It has validation errorsIt moves to errores\ with the load reference. Fix the Excel and copy it into the folder again.
BUFINS rejects it (incomplete template, year not configured…)It moves to errores\ with the reason in a .error.txt file.
Temporary failure (no network, 429, 5xx) or there is a pending load from another personThe file is left in place and retried with increasing wait (up to 30 minutes).

  • Year and mode in the name. A file named 2026_historico_cierre.xlsx is sent as year 2026, historical mode; if the name does not carry them, those in agente.json are used.
  • It does not send half-copied files. It ignores Excel temporaries (~$…) and waits until the file has gone 30 seconds without changes and is not open in another program.
  • No duplicates. It uses the content fingerprint as the Idempotency-Key: copying the same file again does not create another load.
  • Models. With "ejecutarModelos": true, after a confirmed load it asks for the reports to be recalculated and waits for the result (same confirm permission).
  • Logs. They are kept in the logs\ folder next to the agent (30 days). If the watched folder is on the network, the service must run with an account that can access it (the “Local System” account cannot see network drives). Restrict access to the agent's folder: anyone who can read it can use its key.

7. Option B · Sheets as JSON

Three steps: open the load, send each sheet and validate.

Step 1 · Open the load

POST /api/v1/cargues
{ "anio": 2026, "modo": "ejecucion", "idEscenario": 1, "referencia": "October close" }

Responds 201 with the idLote. referencia is free text that BUFINS shows as the “file”.

Step 2 · Send each sheet

POST /api/v1/cargues/236/hojas/Z_SheetName
{ "filas": [
    { "Cuenta": "110505", "Año": 2026, "Mes": 1, "Valor": 1250000.5 },
    { "Cuenta": "110510", "Año": 2026, "Mes": 1, "Valor": 980000 } ],
  "reemplazar": false }
{ "idLote": 236, "hoja": "Z_SheetName", "tabla": "Ini_TableName",
  "filasRecibidas": 2, "filasGuardadas": 2, "filasOmitidasPorAnio": 0, "filasEnHoja": 2, "aviso": null }
  • Send every sheet of your company (those in /esquemas), even if one has no rows ("filas": []). Confirming replaces the year's data: a forgotten sheet would wipe its data, which is why closing requires it.
  • Batches. A large sheet is sent in several calls (maximum 50,000 rows per call); rows are added up. With "reemplazar": true what was sent before for that sheet is discarded and it starts over.
  • All or nothing. If a row in the call has an invalid value, no row of that call is saved and the response indicates the row and column.
  • Year. Rows whose year does not match the load's year are skipped and reported in filasOmitidasPorAnio (same as Excel).
  • Values. Number → JSON number; text → text; Yes/No → true/false; dates → text YYYY-MM-DD; empty → null. Objects and lists inside a row are not accepted. The Año column is also accepted as Anio.

Step 3 · Validate

POST /api/v1/cargues/236/validar

Checks that all sheets were sent and runs the same validations as Excel. Responds with the load status (same shape as Option A). If a sheet is missing: 422 hojas_faltantes with the list. Every time rows are added you must validate again before it can be confirmed.

Complete example in Python
import requests
BASE = "https://customers.bufins.com/api/v1"
H = {"Authorization": "Bearer bfk_..."}

lote = requests.post(f"{BASE}/cargues", headers={**H, "Idempotency-Key": "2026-10-close"},
                     json={"anio": 2026, "modo": "ejecucion", "referencia": "October close"}).json()
id_lote = lote["lote"]["idLote"]

esquemas = requests.get(f"{BASE}/esquemas", headers=H).json()["hojas"]
for hoja in esquemas:
    filas = get_rows_from_erp(hoja["hoja"])              # your function: list of dictionaries
    for i in range(0, max(len(filas), 1), 20000):        # batches of 20,000
        r = requests.post(f"{BASE}/cargues/{id_lote}/hojas/{hoja['hoja']}", headers=H,
                          json={"filas": filas[i:i+20000], "reemplazar": i == 0})
        r.raise_for_status()

res = requests.post(f"{BASE}/cargues/{id_lote}/validar", headers=H).json()
print(res["lote"]["estado"], res["lote"]["totalErrores"], "errors")

8. Review and confirmation

After submission, the load has a status. It is queried with GET /cargues/{idLote}.

StatusWhat it meansWhat next
EnValidacionBeing filled (Option B) or not yet validated.Send sheets and call validar.
ValidadoOkNo errors or warnings.Review and confirmation.
ConAdvertenciasCan be confirmed, but there are warnings to review.A person decides in “Review load”.
ConErroresCannot be confirmed.Fix the data and send again (see findings).
ConfirmadoThe data has replaced the previous data.Run the models to update reports.
DescartadoCancelled without touching data.Send again if needed.

Findings

GET /cargues/{idLote}/hallazgos?max=200 returns, for each problem, the sheet, row, column, rule, a message and a suggestion, plus the real total per rule. Add ?idioma=en for English.

Impact

GET /cargues/{idLote} includes how many rows exist today and how many the load would bring, per table. requiereRevisionHumana indicates a strong reduction (always confirmed by a person) and bloqueado that it cannot be confirmed (golden rule).

Who confirms

A person (default)

The load stays waiting. The company's administrators get a bell-icon notification with the link to “Review load”, where they can review it and confirm or discard it.

The integration (if allowed)

With confirmar=true when uploading or validating, or with POST /cargues/{id}/confirmar. It only confirms loads without warnings or strong reductions; in all other cases it stays pending and notifies a person.

Updating the reports: running the models

Reports are fed by the models. After confirming a load, an integration with permission can ask for them to be recalculated: POST /modelos/ejecutar. Since the calculation can take minutes, the API answers 202 right away with an idEjecucion and the models run in the background, one after another; check progress with GET /ejecuciones/{idEjecucion} until the status is Completada or ConErrores.

{ "idEscenario": 1 }                      (the body is optional; scenario 1 by default)

HTTP 202

  "modelos": [ { "modelo": "PYG",     "estado": "Completado", "mensaje": "Ejecutado correctamente.", "segundos": 8.4 },
               { "modelo": "Balance", "estado": "EnCurso",    "mensaje": null,                        "segundos": null } ] }
  • Statuses: EnCurso (running), Completada (completed), ConErrores (with errors), Interrumpida (the site restarted during the calculation: run them again) and Simulada (testing).
  • One at a time. There can only be one run per company and scenario; another call gets 409 ejecucion_en_curso with the idEjecucion that is running.
  • One error does not stop the others. If a model fails, the rest run and the per-model detail carries its message; the company's administrators get a notification.
  • Permission. It is the same one as confirming loads; without it, 403 permiso_modelos. A testing integration runs nothing (it answers Simulada).

Automatic notifications (webhook)

Instead of polling again and again, BUFINS can notify your system when something happens. The administrator goes to API integrations, clicks the integration's Webhook button and enters your system's URL (https); BUFINS generates a secret (shown only once) and from then on sends a signed JSON POST to that URL.

Verifying the signature

Every notification carries the header X-Bufins-Signature: t={unix seconds},v1={signature}, where the signature is the hexadecimal HMAC-SHA256 of t + "." + body using the secret. Always verify it before trusting the notification, using the exact body received (not reformatted), and reject those older than 5 minutes.

Python
import hmac, hashlib, time

def verificar(secreto: str, cuerpo: bytes, cabecera: str) -> bool:
    p = dict(x.split("=", 1) for x in cabecera.split(","))        # "t=...,v1=..."
    if abs(time.time() - int(p["t"])) > 300:                       # reject old notifications (anti-replay)
        return False
    esperado = hmac.new(secreto.encode(), p["t"].encode() + b"." + cuerpo, hashlib.sha256).hexdigest()
    return hmac.compare_digest(esperado, p["v1"])
C#
static bool Verificar(string secreto, string cuerpo, string cabecera)
{
    var p = cabecera.Split(',').Select(x => x.Split('=', 2)).ToDictionary(x => x[0], x => x[1]);
    if (Math.Abs(DateTimeOffset.UtcNow.ToUnixTimeSeconds() - long.Parse(p["t"])) > 300) return false;
    var esperado = Convert.ToHexString(HMACSHA256.HashData(
        Encoding.UTF8.GetBytes(secreto), Encoding.UTF8.GetBytes(p["t"] + "." + cuerpo))).ToLowerInvariant();
    return CryptographicOperations.FixedTimeEquals(Encoding.ASCII.GetBytes(esperado), Encoding.ASCII.GetBytes(p["v1"]));
}
  • Answer with a 2xx within 15 seconds and process afterwards. Any other response is considered failed.
  • Retries: up to 3 attempts (immediate, after 30 seconds and after 5 minutes). If all fail it is left as Failed on the integration screen; pending ones are resumed with the API's next activity.
  • It may arrive repeated. Use X-Bufins-Delivery (or the id field) to ignore notifications you already processed.
  • Safe destination. Only https and public internet addresses: BUFINS does not send to internal networks, nor follow redirects.
  • Lost secret: “Generate new secret” invalidates the old one instantly; update your system.

In the testing environment confirmation is simulated: the response carries "estado": "ConfirmadoSimulado" (or "confirmacion": "simulado" when uploading with confirmar=true) and the test load is discarded without touching data.

Before replacing, BUFINS automatically saves the previous version. If a confirmed load turns out to be wrong, an administrator can undo it from the Version history.

11. Best practices

Repeat without duplicating

Send Idempotency-Key on POST /cargues and /cargues/archivo, with a unique value per logical submission (for example “company-year-month-sequence”). If the call is repeated because of a network failure, BUFINS returns the load already created ("repetido": true) instead of creating another. The key is remembered for 7 days.

Frequency

One submission daily, weekly or monthly is enough: the information is financial, not transactional. Each submission carries the full year to date and replaces the previous one; repeating it does not duplicate data.

Retries

On 429 or 5xx wait and retry with the same Idempotency-Key. On 4xx fix first: retrying unchanged will not solve it.

How long a load lasts

A load waiting for review is kept for 48 hours; one being filled by sheets, 6 hours. After that it is discarded and must be sent again.

Size

The template can weigh up to 100 MB. In Option B use batches of 20,000 rows or fewer per call (the maximum is 50,000).

Testing

Develop first with a Testing integration (bft_ key): it runs the whole flow without touching real data. Once in production, start with human confirmation active and compare the results with Excel for a few closes before asking for the integration to confirm on its own.

12. Frequently asked questions

Do I have to stop using Excel?

No. Excel keeps working at all times, through the same door and with the same validations. The API is an alternative; you can alternate them.

What happens if I send the same thing twice?

With the same Idempotency-Key BUFINS does not duplicate it. Without it, the second submission replaces the first if it was still pending; if the first was already confirmed, the second is reviewed and replaces the year's data, like a new Excel load.

Why “cannot be confirmed”?

Check /cargues/{id}/hallazgos. If it has errors the data must be fixed; if the impact shows bloqueado, the file would leave a year empty or a table almost empty and BUFINS prevents it for everyone.

Does the API update the reports?

A confirmed load leaves the data ready; reports read the results of the models. An integration with permission recalculates them with POST /modelos/ejecutar; otherwise they are run in “Model execution”, as always.

How do I find out when a person confirms the load?

Configure a webhook: BUFINS sends you cargue.confirmado as soon as someone confirms it in “Review load”. If you cannot receive notifications, poll GET /cargues/{id} from time to time.

Can I see the loads of another integration or of the company's people?

No. Each integration only sees the loads it created itself. People see them in “Review load”.

I lost the key, what do I do?

An administrator goes to API integrations and clicks “Generate new key”. The old one stops working instantly; set the new one in the client's system.

Is my data protected?

It travels encrypted (HTTPS), each key reaches only one company and everything the integration does is in the audit log. BUFINS acts as a data processor for the company's data; the data transmission agreement is arranged separately.
